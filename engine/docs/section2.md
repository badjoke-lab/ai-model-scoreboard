# 🟥 **AI Model Scoreboard v4 – 内部仕様書（完全版）**

## **Section 2 – Performance Score（性能スコア）〈最終仕様〉**

---

# **2-1. 概要（Purpose）**

Performance Score は
**「客観ベンチマークによって測定されたモデル能力」**
を定量化した指標である。

採用するデータは以下のみ：

* **第三者による標準ベンチマーク（LM Eval Harness 等）**
* **Chatbot Arena Elo（四半期ごとに固定スケール）**
* **ベンダー公式ベンチ（※重み減衰）**

逆に以下は絶対に使用しない：

* 口コミ・SNS評判・レビュー
* ブログ・宣伝記事
* 人間による主観評価
* 不安定なコミュニティベンチ（root不明の測定）

---

# **2-2. Performance Score の構造**

Performance は以下 4 つのファミリーに分割して評価する。

| ファミリー名                | 対応領域        | 例となるベンチ                                  | 重み       |
| --------------------- | ----------- | ---------------------------------------- | -------- |
| **General Reasoning** | 一般推論・QA     | MMLU / MMLU-pro / BigBench               | **0.40** |
| **Coding Ability**    | コード性能       | HumanEval / MBPP / Code Generation evals | **0.30** |
| **Math & STEM**       | 計算・数学・論理    | GSM8K / MATH                             | **0.20** |
| **Chat Quality**      | 対話品質・主観的快適性 | Arena Elo / 対話系ベンダーベンチ                   | **0.10** |

この構造は **用途の異なるベンチを混ぜて平均値にしないため** に絶対の前提とする。

---

# **2-3. ファミリー内の計算方式**

各ファミリーは **0〜100 のスコア** に正規化してから統合する。

## ■ (1) 正規化基準（Normalization Policy）

1. **四半期ごとに「基準表」を固定して更新する**

   * Q1/Q2/Q3/Q4 ごとに “トップモデル値” と “最低実用ライン値” を固定
   * 毎日の変動で点数が揺れないようにする

2. 正規化式（線形）

```
normalized_score = 
   (raw_score - min_baseline) / (max_baseline - min_baseline) * 100
```

3. **min_baseline を下回る場合は自動で 0、max_baseline を超える場合は自動で 100 にクランプ**

---

## ■ (2) ベンチデータの重み付け

各ベンチマークは以下のルールで重み付けする。

### ★ 第三者ベンチ（LM Eval / Harness 系）

→ **weight = 1.0（満額反映）**

### ★ ベンダー提供ベンチ（GPT Accuracy など）

→ **weight = 0.5（半額反映）**

### ★ 未確認ベンチ / コミュニティ検証

→ **使用禁止（raw データとして採用しない）**

---

## ■ (3) ファミリー内合成式

ファミリー内に複数のベンチがある場合：

```
family_score = 
    Σ(normalized_score_i * weight_i) / Σ(weight_i)
```

---

## ■ (4) データ欠損処理

1. ファミリー内に **1つでも第三者ベンチがあれば計算可能**
2. すべて欠損（第三者ベンチなし・自称値もなし）
   　→ そのファミリーは **“欠損” として除外**
3. ファミリーが **2つ未満しか算出できない場合**
   　→ 最終スコアは計算するが
   　→ **モデル全体は Provisional（一次採用）扱いに強制する**

（性能評価の信頼性不足のため）

---

# **2-4. Chat Quality（Chat ファミリー）の特例**

Chat Quality は以下の構造で算出する：

```
chat_quality_score = 
    arena_component * 0.7 +
    vendor_chatbench_component * 0.3
```

### ■ Arena Elo（四半期固定）

* Arena は母集団が常に変わるため、
  **“四半期ごとにスケールを固定した Elo→0〜100 の変換表”** を作成し
  その期間中は値を固定する。

* これにより
  「今週急に Elo が変動したから全モデルのスコアが乱高下する」
  という現象を止める。

### ■ vendor 任意ベンチ

* 「対話評価（ベンダー独自試験）」があれば
  weight=0.5 の補正で取り込む。
  （自称値が強すぎないようにする）

---

# **2-5. Performance Score の最終計算式**

```
performance = 
    general_reasoning_score * 0.40 +
    coding_score            * 0.30 +
    math_score              * 0.20 +
    chat_quality_score      * 0.10
```

* 1ファミリー欠損 → 残り3つで重み再正規化
* 2ファミリー欠損 → Score は出すが Provisional 扱い
* 3ファミリー欠損 → Performance 評価不可 → モデルは Provisional（性能不明）
* 全欠損 → Rejected（スコアリング対象外）

---

# **2-6. Provisional（一次採用）との連動規則**

以下の条件を満たしたモデルは、
**Performance Score がいくら高くても Full Listing には昇格できない。**

### ■ Provisional 条件（Performance 観点）

1. **第三者ベンチが2系統未満**
2. **Chat Quality 以外の全ファミリーが欠損**
3. **ベンダー自称値しかない場合**
4. **ベンチマークが極端に古い（半年以上更新なし）**

この状態のモデルは
「性能の推定精度が低い」ため、Full に上がらない。

---

# **2-7. 目的（この仕様の効果）**

この体系は以下を実現する：

1. **SNSや人気投票に操作されない**
   → Arena は 10% ファミリーの中の 70% → 実質 Performance 全体の **7%** 程度に圧縮
2. **用途の違いが潰れない**
   → コード特化・数学特化モデルが正当に評価される
3. **データ欠損に強い**
   → ベンチが無いモデルでも評価は可能（ただし Provisional）
4. **毎日スコアが揺れない**
   → 全て四半期ごとに基準固定
5. **将来のモデル追加に耐える**
   → GPT 6、Claude 4.2、Gemini 3、Llama 5 等が出てもそのまま評価可能

## **Section 2 – Safety & Reliability Score（安全性・信頼性）〈最終仕様〉**

---

# **2-8. 概要（Purpose）**

Safety & Reliability Score は **「モデルが壊れないか」「ユーザー資産を危険に晒さないか」「安全性に対してどれだけ正式な取り組みをしているか」** を数値化する指標である。

目的は以下の**2つの軸**に集約される：

1. **Safety Posture（安全性の“設計姿勢”）**
2. **Incident History（実際に起きた問題の履歴）**

SNSの噂話や印象論は対象外。
「公式に残っている事実」だけを扱う。

---

# **2-9. 情報源（Data Sources）**

スコアは必ず以下から取得する客観データのみで構成される。

### ■ 公式情報

* ベンダー公式モデルカード
* 安全性ポリシー / RLHF ガイドライン
* 安全性に関するホワイトペーパー・透明性レポート
* ベンダーが公開するインシデント報告

### ■ 第三者情報

* 外部 red-team audit レポート
* セキュリティ企業・研究機関の脆弱性分析（CVSS 記録など）

### ■ 使用禁止

* SNS炎上
* 匿名の告発
* Reddit/Discord の噂
* 有名インフルエンサーの主張
* 「なんとなく危険っぽい」という印象

---

# **2-10. スコア構造（全体）**

Safety & Reliability は **100点満点** で構成し、以下の2ブロックで計算する。

| ブロック名                      | 内容               | 配点      |
| -------------------------- | ---------------- | ------- |
| **Safety Posture（設計姿勢）**   | 企業・モデルの安全性への取り組み | **60点** |
| **Incident History（事故履歴）** | 実際に起きた問題と再発防止    | **40点** |

---

# 🟦 **2-11. Safety Posture（60点）**

**チェックリスト方式で完全に機械化**する。
曖昧な「なんとなく安全そう」は禁止。

項目は以下：

## ✔ A. モデルカードの安全性セクション（最大 10 点）

* 安全性に関する記述あり： +5
* 高リスク領域の明示（例：医療・法律・金融）： +5

## ✔ B. 訓練方針の説明（最大 10 点）

* RLHF / alignment 手法の基本説明： +5
* データ構成カテゴリの概要開示： +5

## ✔ C. Misuse / Harm Prevention（最大 10 点）

* 悪用防止ポリシーの明文化： +5
* 有害出力を制御するメカニズムの説明： +5

## ✔ D. External Audit / Red-teaming（最大 20 点）

* 外部 red-team 実施・結果公開： +10
* Independent audit（第三者監査）の実施： +10

## ✔ E. Yearly Transparency Update（最大 10 点）

* 12ヶ月以内に安全性関連の公式アップデートあり： +10

---

# 🟥 **2-12. Incident History（40点）**

初期値を **40 点満点（=安全履歴クリーン）** とし、
インシデントの種類ごとにペナルティを適用する。

インシデントは 3 階層に分類する。

---

## ■ 1. Minor Incident（軽度）

例：

* 一時的な hallucination バグ（公式に認められ修正）
* 部分的な不具合でユーザーへの影響が限定的

### → ペナルティ： **-5 点**

### → 回復： 6ヶ月で **+2 点** 自動回復

---

## ■ 2. Major Incident（重大）

例：

* 大規模なデータリーク
* 高リスク領域で誤出力により実害発生
* モデルの重大な misalignment が公式に確認された場合

### → ペナルティ： **-20 点**

### → 回復： 12ヶ月で **+10 点** 自動回復

---

## ■ 3. Critical Incident（致命的）

例：

* モデルの「全面撤回」や「提供停止」を伴う重大欠陥
* 高リスク領域で甚大な実害を引き起こした問題
* バックドア・深刻なデータ汚染

### → ペナルティ： **-40 点**（= Incident Score が 0）

### → 添付規則： **モデルは原則 Rejected に即移行**

（後で復活させる場合は、Version Upgrade 扱いとして新モデル扱い）

---

# 🟥 **2-13. Incident History の計算式**

```
incident_score = 
  max(0, 40 
        - (minor_count  * 5)
        - (major_count  * 20)
        - (critical_count * 40)
        + recovery_points)
```

※ recovery_points は半年・1年ごとに自動加算される（最大で incident_score=40 まで）

---

# 🟥 **2-14. Safety & Reliability Score（最終計算式）**

```
safety_score = 
    safety_posture_score * 0.60 +
    incident_score       * 0.40
```

---

# 🟥 **2-15. Provisional / Rejected との連動規則**

### ■ Provisional（一次採用強制）条件

以下のいずれかに該当すると Full Listing に上がれない：

1. External audit が一度もない
2. Safety posture が 30 点未満
3. Incident score が 20 点未満
4. 安全性に関する公式情報がほとんど公開されていない場合

### ■ Rejected 条件（安全性による除外）

1. **Critical incident の発生**
2. **重大な安全性の欠陥が是正されず継続している場合**
3. **安全性情報が意図的に隠蔽されていると公式に指摘された場合**
   （※SNSの“疑惑”は除外。公式記録だけ）

---

# 🟥 **2-16. この仕様の効果（狙い）**

1. **SNSの風評被害を排除する**
   　→ 公式と第三者レポートだけが評価対象

2. **“設計姿勢”と“実害履歴”を分けることで、正義・悪評の区別が明確になる**

3. **時間とともにインシデントを過剰に引きずらない**
   　→ 半年・1年で部分回復（現実的運用）

4. **外部監査をしていないモデルは Full に上げない**
   　→ 安全性の標準が上がり、モデル業界全体の品質向上につながる

## **Section 2 – Adoption & Support Score（採用・基盤・安定性）〈最終仕様〉**

---

# **2-17. 概要（Purpose）**

Adoption & Support Score は以下 3 要素を評価する：

1. **Ecosystem（エコシステム・周辺ツール）**
2. **Stability（稼働安定性・信頼性）**
3. **Freshness（更新の新しさ・維持されているか）**

**“実務で安心して使えるモデルか” を数字で示す指標**。

SNSの盛り上がり・YouTube の推し・界隈の人気投票は一切使わない。

---

# **2-18. スコア構造（比率）**

| 指標                  | 内容                    | 比率      |
| ------------------- | --------------------- | ------- |
| **Ecosystem Score** | SDK / OSS / ツール連携の充実度 | **40%** |
| **Stability Score** | 稼働率・障害の少なさ            | **30%** |
| **Freshness Score** | 更新頻度・維持されているか         | **30%** |

合計 100%。

Performance や Safety と比べて **“経年での実務利用に耐えうるモデルか”** を中心に評価する。

---

# 🟦 **2-19. Ecosystem Score（40 点）**

エコシステムの充実度＝「実務で使いやすいか」を完全に機械化したチェックリストで判定する。

## ✔ エコシステム項目（合計 40 点）

### ■ SDK / API クライアント（最大 15 点）

* 公式クライアント（JS, Python, Go, Java）が全て揃っている：+10
* 主要フレームワーク向け SDK 提供（LangChain 互換など）：+5

### ■ OSS 連携（最大 10 点）

* GitHub 上の OSS コネクタ（1,000★以上）が存在：+5
* コミュニティによる安定メンテナンスが確認できる：+5

### ■ ドキュメント品質（最大 10 点）

* API Reference が体系的で更新日記載あり：+5
* サンプルコードが主要言語に提供されている：+5

### ■ 総合 Developer Experience（最大 5 点）

* バージョニングが適切（SemVer等）：+2
* 明確な changelog を提供：+3

**計 40 点満点。**

主観なし、SNS関係なし。
**存在の有無と質だけを見る。**

---

# 🟦 **2-20. Stability Score（30 点）**

モデルの運用安定性を評価する。

## ✔ Stability 計算式

```
stability_score = 
    uptime_component * 0.70 +
    incident_component * 0.30
```

### ■ uptime_component（基準：90日間の稼働率）

| 稼働率        | 点   |
| ---------- | --- |
| 99.9%以上    | 100 |
| 99.0〜99.9% | 90  |
| 98.0〜99.0% | 75  |
| 95.0〜98.0% | 55  |
| 95.0%未満    | 40  |

（API status page のログから取得）

※ 点は後に 0〜30 へ線形換算する。

### ■ incident_component

Safety の Incident History とは別枠。
「APIの運用事故・つながらない・極端なレイテンシ上昇」などの **非安全系インシデント** の回数で決める。

* Minor API outage（数分〜数十分）： -2
* Major outage（1時間以上）： -5
* Multi-region outage： -10

合計点は最大 100 → 0〜30 に線形換算。

---

# 🟦 **2-21. Freshness Score（30 点）**

「モデルが今もメンテナンスされているか」を評価。
**“更新が多いほど良い” ではなく、“長期間放置されていないか” を見る。**

### ✔ Freshness 点数表

| 最終更新からの経過日数 | 点   |
| ----------- | --- |
| 0〜90日       | 100 |
| 90〜180日     | 80  |
| 180〜365日    | 60  |
| 365〜540日    | 40  |
| 540日以上      | 20  |

→ 0〜30 点に線形換算。

### ポイント：

* **細かい更新を大量にしても加点は伸びない**（過剰評価防止）
* 「きちんと保守されているか」が見るべき本質

例）
Claude 3 や GPT-4.1 のように年数回の大型更新だけでも 0〜90 日以内が多いため高スコア。

---

# 🟥 **2-22. Adoption & Support の最終式**

```
adoption_score =
    ecosystem_score * 0.40 +
    stability_score * 0.30 +
    freshness_score * 0.30
```

* 全て客観データ
* SNS指標ゼロ
* “実務で安心して使えるか” をそのまま反映

---

# 🟥 **2-23. Provisional / Rejected との連動規則**

### ■ Provisional（一次採用）条件

以下のいずれかに該当すると Full Listing に上がれない：

1. ecosystem_score < 15
2. uptime_component < 75（＝稼働率が 98% を下回る）
3. freshness_score < 40（＝一年以上更新放置）
4. ドキュメントが極端に不足している（API仕様が最低限レベル）

### ■ Rejected 条件

以下に該当すると Full / Provisional どちらにも載せない：

1. 稼働率が継続的に 95% 未満
2. 540日以上更新がない（放棄と見なす）
3. API 基礎機能が壊れている期間が長い
4. 重大 API 障害が繰り返され改善がみられない

---

# 🟥 **2-24. この仕様の狙いと効果**

1. **「更新が多い＝良い」という誤解を排除**
   　→ 重要なのは“ちゃんと保守されているか”

2. **SNS人気・注目度ではなく“実務利用のしやすさ”を評価**
   　→ SDK / OSS / ドキュメント / 安定性 がそのまま反映される

3. **障害が多いモデルは自然にスコアが下がる**
   　→ 稼働性の良いモデルが上位へ

4. **放置されているモデルは自動的に Provisional / Rejected へ流れる**
   　→ “死んでるモデル” が一覧に残らない

5. **Codex 実装に耐える完全機械化仕様**
   　→ チェックリストと数値閾値だけで評価可能

## **Section 2 – Openness & Transparency Score（透明性）〈最終仕様〉**

---

# **2-25. 概要（Purpose）**

Openness & Transparency Score は、

**「モデルの構造・訓練方針・データ情報・リスク・制限をどれだけ明確に開示しているか」を評価する指標。**

* **オープンモデル（OSS）だから高得点**
* **クローズドだから低得点**

という思想ではない。

目的は **説明責任と透明性の水準を評価することであって、公開範囲の広さ競争をすることではない。**

---

# **2-26. 情報源（Data Sources）**

透明性評価に使うデータ：

### ■ 公式情報

* モデルカード
* 技術レポート / ホワイトペーパー
* 訓練データ方針の公開文
* API・モデル仕様書
* ベンダーの透明性レポート（transparency report）

### ■ 第三者情報

* 外部レビュー（技術レビュー）
* 認証・標準化団体による評価（NIST等）

### ■ 使用禁止

* SNSの噂
* 「このモデルは絶対オープンじゃない」など主観
* 断片的なリーク情報

---

# **2-27. スコア構造**

Openness & Transparency Score は **100点満点** とし、
以下 5 項目の **チェックリスト合計（60点）→線形換算で100点に補正** する。

| 観点                                    | 目的          | 配点                  |
| ------------------------------------- | ----------- | ------------------- |
| Model Card Quality                    | 中核情報の開示     | 15                  |
| Data & Training Disclosure            | 訓練データ方針の透明性 | 15                  |
| Architecture / Technical Transparency | 構造の説明       | 10                  |
| Safety Disclosure                     | リスク・制限の説明   | 10                  |
| External Review / Openness Signals    | 外部検証・姿勢     | 10                  |
| **合計**                                |             | **60 点 → 100 点に換算** |

---

# 🟦 **2-28. 各項目のチェックリスト**

## ✔ A. Model Card Quality（最大 15 点）

| 項目                        | 点  |
| ------------------------- | -- |
| モデルカードが存在する               | +5 |
| モデル概要・用途が明確               | +5 |
| 制限事項（limitations）が明示されている | +5 |

---

## ✔ B. Data & Training Disclosure（最大 15 点）

※ 訓練データの「全文公開」などを求めるものではない。
※ カテゴリ・方針・構成比などの **概要透明性** を評価する。

| 項目                                        | 点  |
| ----------------------------------------- | -- |
| 訓練データソースのカテゴリ開示（web / code / synthetic 等） | +5 |
| データフィルタリング方針の説明                           | +5 |
| 著作権・利用許諾に関する立場表明                          | +5 |

---

## ✔ C. Architecture / Technical Transparency（最大 10 点）

クローズドモデルでも構造の概要開示は可能。

| 項目                                    | 点  |
| ------------------------------------- | -- |

| 項目                              | 点  |

| 外部研究機関のレビューを受けている               | +5 |
| 透明性レポート（transparency report）の公開 | +5 |

# 🟥 **2-29. 計算式（Openness Score）**

```
raw_openness_score = 
    (model_card_points +
     data_disclosure_points +
     architecture_points +
     safety_disclosure_points +
     external_review_points)  // 最大60

openness_score = (raw_openness_score / 60) * 100
```

* 端的に言うと「チェックリスト 60 点分を 100 点満点に外挿」する方式
* これにより主観介入を完全排除できる

# 🟥 **2-30. Provisional / Rejected との連動規則**

## ■ Provisional（一次採用）条件

以下のいずれかに該当すると Full Listing に上がれない：

1. モデルカードが存在しない
2. data_disclosure_points = 0（訓練データ方針が完全ブラックボックス）
3. safety_disclosure_points = 0
4. raw_openness_score < 20（60点満点で 20 点未満）

→ 「透明性最低基準に達していない」と判断

---

## ■ Rejected 条件

1. **公式情報の提供が意図的に拒否されていると明記された場合**
   （例：透明性評価を拒絶するベンダーステートメント）
2. **透明性に関する深刻な誤解・虚偽記述が公式に認定された場合**
3. **モデルカード・訓練方針・安全情報が一切存在せず、半年以上改善がない場合**

# 🟥 **2-31. この仕様の効果（狙い）**

   * 「説明責任」「開示姿勢」だけを見る

   * 必要最低限の情報開示があれば高得点可能

3. **LLM界隈の価値観の変化にも耐える**

   * データ開示の義務化などが起きても仕様はそのまま使える

   * チェックリストなので曖昧な判断が不要

# 🟥 **AI Model Scoreboard v4 – 内部仕様書（完全版）**

## **Section 2 – Cost Efficiency Score（費用効率）〈最終仕様〉**

---

# **2-32. 概要（Purpose）**

Cost Efficiency Score は、
**「同じ仕事をさせるとき、どれだけ安く済むか」**
を公平に評価する指標。

* 価格表（pricing page）
* 標準料金プラン（pay-as-you-go）
* input/output token 単価
  のみを使用する。

SNSでの「安い高い騒ぎ」や、体験談ベースの「コスパ最強！」などの主観は完全排除。

---

# **2-33. 情報源（Data Sources）**

使用するデータは以下に限定：

### ■ 必須データ

* 公式 pricing ページの
  **input tokens 1K単価**
  **output tokens 1K単価**
* context length による追加料金（あれば反映）

### ■ 参考データ（任意）

* ベンダーの pricing API

### ■ 使用禁止

* SNSの「安いらしい」
* 非公式ブログの表
* 価格比較動画やレビュー
* 国別為替レート（※ドル建てで統一）

---

# **2-34. 標準シナリオ（Standard Cost Scenario）**

**全モデルを同一条件で比較するため、
“標準入力 → 標準出力” のコストを1点だけ算出する。**

### 標準入力（Standard Input）

```
1000 tokens（input）
```

### 標準出力（Standard Output）

```
300 tokens（output）
```

※ 実際の多くのユースケースで「input の方が長い」傾向があるため、
input:output は **70% : 30%** に固定。

---

# **2-35. Raw Cost（生コスト）の算出式**

```
raw_cost = 
    (input_1k_price * 1.0) +
    (output_1k_price * 0.3)
```

例

* 入力 → $5 / 1K
* 出力 → $15 / 1K

なら：

```
raw_cost = 5 * 1.0 + 15 * 0.3 = 5 + 4.5 = $9.5
```

---

# **2-36. Raw Cost の補正規則**

以下の場合は補正する。

## ■ 補正A：context length に明らかな制限があるモデル

* 公式 context が極端に短い（例：2K tokens）
  → -10% のペナルティ（効率低下とみなす）

## ■ 補正B：無料モデル

* raw_cost は **最低値よりさらに下がらないように**
  → “無料だから常に100点” を防止する

具体的には：

```
if raw_cost == 0:
    raw_cost = min_nonzero_cost * 0.8
```

（ = 最安有料モデルの 80% と扱う）

---

# **2-37. 正規化（Normalization）**

quarterly（四半期ごと）に業界の主要モデルを基準に
**「min_cost」 と「max_cost」** を固定する。

```
normalized_cost_efficiency = 
    (max_cost - raw_cost) / (max_cost - min_cost) * 100
```

* 最安 → 100
* 最高 → 0
* 中間 → 線形スケール
* min/max の揺れは四半期で固定して安定運用

---

# **2-38. Ceiling（上限）処理**

極端に安いモデルが
**性能無視でランキング最上位に来ることを禁止**するため、
コストスコアは **最大 100 で固定（超過なし）**。

さらに、**Weight（最終得点への影響）は 10%** に固定。
（→ コストが安いだけの低品質モデルが総合上位に来るのを防ぐ）

---

# **2-39. Cost Efficiency Score（最終式）**

```
cost_efficiency_score = normalized_cost_efficiency
```

そのまま 0〜100 点。
最終 Ranking では以下で計算：

```
final_score_component = cost_efficiency_score * 0.10
```

---

# **2-40. Provisional / Rejected との連動**

### ■ Provisional 条件（一次採用）

以下の場合、コストの精度が不十分とみなす：

1. input / output 単価が公開されていない
2. pricing 情報が古い（180日以上更新なし）
3. context length の制限が極端（< 2K tokens）

→ モデルはスコアは出すが Full Listing には上げない。

### ■ Rejected 条件（コストによる除外）

以下の場合、Cost Score は生成されず採用不可：

1. 価格が不明でベンダーが公開を拒否している
2. 料金体系が不透明（従量単価が存在しない・問い合わせ専用）
3. 不正確または矛盾した価格情報が公式に指摘された場合

→ “評価不能モデル” として Rejected に分類される。

---

# **2-41. この仕様の効果（狙い）**

1. **価格差を公平に比較できる**
   → input/output を統一シナリオにして比較

2. **安すぎるモデルが無双しない**
   → 性能スコアとは直接掛け合わせず、影響力を 10% に抑制

3. **無料モデルの過剰優遇排除**
   → “0円だから100点” にならない設計

4. **仕様が極めて機械的で Codex が自動処理しやすい**

5. **四半期で基準固定 → ランキングが安定**
   → 毎日の小変更でスコアが暴れない
