# 🟥 **AI Model Scoreboard v4 – 内部仕様書（完全版 / 非公開）**

## **Section 1 – モデル採用・昇格・降格ルール**

---

# **0. 目的**

AI Model Scoreboard v4 は、
**「実在するモデルの性能・安全性・運用実態に基づく透明性評価」**
を目的とし、各モデルの採用・昇格・降格を
**完全自動ルールにより機械的に判断する体系** を持つ。

本仕様書の原則は以下：

* 評価は公平で説明可能・再現可能であること
* 特定ベンダーへの忖度を排除すること
* 一度決めたスコアリング体系は AI が再構築可能であること
* 「Methodology ページ＝この仕様書の簡略公開版」として扱えること

---

# **1. モデル分類（3段階）**

Scoreboard に掲載するモデルは以下 3 クラスに分類される。

## **1. Full Listing（正式掲載モデル）**

### 条件

* スコアリング要件をすべて満たす
* 更新頻度（updatedAt）が健全
* 安全性インシデントが基準未満
* 外部エビデンスが十分に確保されている

### 表示

* 通常スコアリング
* UI 上でフルカード表示
* Methodology の全項目が適用される主対象モデル

---

## **2. Provisional（暫定掲載 / 情報不足モデル）**

### 条件

以下のいずれかに該当：

1. **情報不足系**

   * 公開情報が極端に少ない
   * updatedAt が古くなってきている（後述）

2. **新規モデル系**

   * リリース直後で安定性が不明
   * 評価用の外部ベンチがまだ揃わない
   * 大幅アップデート後の過渡期

3. **リスク警戒系**

   * インシデント 2件 → 即 Provisional 降格
   * ただし即リジェクトではない（1件は誤情報の可能性を残すため）

### 表示

* 「Provisional」バッジ
* 一部スコアに“推定値”が含まれることを明示
* 評価は行うが信頼度が低いことを明確にする

---

## **3. Rejected（不採用 / 掲載しない）**

### 条件

### **A. 自動的に Rejected となるケース**

* **重大インシデント 1件**
  (ベンダー公式の安全性関連 acknowledgment がある場合)
* 安全性インシデント **3件以上**
* 情報の信頼性が破綻（虚偽・捏造・詐称等）

### **B. 降格連鎖による Rejected**

後述の「更新頻度ロジック」により

* Provisional がさらに 60日更新なし
  → 自動的に Rejected へ移行

### 表示

* UI には **掲載されない**
* Methodology や公開版には「当該モデルは現在評価対象外」とのみ記載可能
* 内部ログには降格理由を保持する

---

# **2. 昇格ロジック（Automatic Promotion）**

## **Provisional → Full Listing 昇格条件**

次の 3つをすべて満たす時、自動的に正式掲載へ昇格。

1. **updatedAt が直近 30日以内**
2. スコアリング項目が全て取得可能
3. インシデント 0〜1件

   * 1件の場合は「モデル仕様変更で改善された」などの追加証跡（自動評価）が必要

昇格は

* 毎日0:00 UTCバッチ
* または API リクエスト時の lazy 更新
  のどちらかで実装可能。

---

# **3. 降格ロジック（Automatic Demotion）**

## **Full Listing → Provisional 降格条件**

### **A. 更新頻度（updatedAt）に基づく降格**

あなたとの議論で決定した最適ライン：

* **90日更新なし → Provisional へ降格**

#### 理由

* 業界標準の更新頻度（1〜3ヶ月）に一致
* GPT / Claude / Llama / Gemini / Orion 系すべてに適用可能
* MVP 時点の掲載モデル数を極端に削らない

---

### **B. 安全性インシデントに基づく降格**

* **インシデント2件 → 即 Provisional**

**インシデントとは：**

* ベンダーが公表する安全性問題
* 外部監査レポートの “confirmed” 事故
* 複数ソースで一致した危険挙動が再現可能なケース（内部ルールで定義）

---

## **Provisional → Rejected 降格条件**

### A. 更新頻度

* **Provisional 状態でさらに 60日更新なし → Rejected**

※ 新旧モデル混在時に古いモデルが自然に排出される。

---

### B. インシデント

* **インシデント3件 → 即 Rejected**
* **重大安全事故1件 → 即 Rejected**

---

# **4. 新規モデルの扱い**

AI モデルは突然現れることが多く、
“情報不足なだけで Rejected される” のは不公平であるため、
以下ルールを採用する。

### **新規モデルは必ず Provisional スタート**

* 情報が揃い次第 Full Listing 昇格
* 情報が揃わず 90日経過 → Provisional のまま
* さらに 60日（計150日）経過 → Rejected（除外）

### 新規登場時に特別扱いしない

* GPT 5.1 でも未知のベンダーでも同じフロー
* 「特別昇格」や「優先掲載」は禁止
* ただし内部で “Featured: New Model” の UI バッジは許可（Optional）

---

# **5. バージョンアップの扱い（モデルの世代交代）**

AI モデルは

* GPT-4 → GPT-4 Turbo → GPT-4.1 → GPT-5 系
* Claude 2 → Claude 3 → Claude 3.5 → Claude 4
  のように **バージョン番号が変わる場合**がある。

### **扱い方**

* **別モデルとして新規採用（Provisional）扱い**
* 旧モデルは updatedAt が進まないため自然に降格→除外
* 同シリーズでも世代は混在可能（Scoreboard 上で区別）

### 理由

* “モデルの性質＝学習データとアーキテクチャ” が全く違うため
* 旧版と新版の差をユーザーに明確にすると信頼性が高まる

# **6. 採用・降格の自動化スケジュール**

## 一日の流れ（自動バッチ案）

00:00 UTC

1. snapshot.json の取得
2. updatedAt の自動評価
3. インシデントログ参照
4. 全モデルのステータス更新
5. 不要モデル（Rejected）の除外
6. UI のリビルド（Vercel ISR）

または「リクエスト時に lazy 更新」も許可。
